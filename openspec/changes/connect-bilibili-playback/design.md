# Bilibili 真实接入设计

日期：2026-11-16。状态：用户已明确开始开发；本文件包含最后确认的三种登录方式与双位置播放器。

## 1. 目标与已确认范围

在现有 Electron + React 桌面壳内完成：扫码 / 账号密码 / 手机验证码登录 → 确认绑定手机号 → 取得本软件首页推荐的首个普通视频 → 在聊天卡片或右侧窗口有声播放并切换画质。

账号登录在本机跨重启保存，仅主动退出或明确检测到过期后要求重新登录。左下角齿轮下方显示 B 站头像，提供 Codex 风格账号菜单和 Profile 页面。

Profile 展示头像、昵称、UID、会员和手机号绑定状态、退出登录。收藏夹、观看历史、关注列表只留入口，不请求相应数据。不做独立账号系统、资料编辑、弹幕、下载、投稿、番剧或付费内容解锁。

## 2. 路线比较与选择

| 路线 | 优点 | 代价 | 决策 |
| --- | --- | --- | --- |
| A：扫码、社区主站接口、自有播放器 | 沿用现有外观，可控的账号和画质交互 | 主站接口变化时需要维护 | 用户已选择 |
| B：社区首页接口、嵌入 B站网页播放器 | 播放细节交由网页处理 | 样式、登录态和控制能力受网页限制 | 未选择 |
| C：先申请官方开放平台 | 官方授权范围明确 | 需要入驻审批，当前不能确认覆盖个人推荐和播放 | 未选择 |

API collect 是社区文档，不是 SDK。参考其协议及 wiliwili 的实现思路，不整体引入 C++ 客户端或已归档 Python 库。第三方项目代码和文档使用遵循各自许可；不假定整个客户端可直接复制。本阶段不承诺社区接口长期不变。

## 3. 用户流程

### 登录与绑定状态

未登录时，头像位置使用与现有界面一致的账号图标，点击打开包含扫码、账号密码、手机验证码三个页签的登录面板。密码和验证码在隔离的 B站官方窗口输入，自动切换官方对应页签；本应用不收集密码或验证码。官方人机验证由用户完成。扫码在应用内显示。展示二维码并按接口要求轮询；扫码成功后获取账号信息。二维码过期时允许手动刷新；关闭面板或成功后停止轮询。

手机号检查采用登录信息的 mobile_verified（具体返回以实际接入为准）。明确已绑定才进入推荐和播放；未绑定时提供前往 B站账号安全页面的入口，用户自行完成绑定后点“重新检查”。字段缺失或请求失败显示“暂时无法确认”，不当作已绑定，也不清除登录。

启动时恢复本地凭证并查询会话与绑定状态。网络失败保留凭证，提供手动重试；明确未登录/过期才转入扫码状态。已保存的资料可以显示，但检查未完成前不作为绑定通过的证据。不建立定时后台刷新服务，第一版不实现复杂 Cookie 续期流程。

退出登录清除本应用的本地会话、账号资料与播放器资源；不触发其他设备退出。一次只管理一个 B站账号。

### 头像与 Profile

入口放在 ActivityRail 齿轮下方。点击头像打开账号菜单，再进入 Profile。该交互依据当前 Codex 包中的 profileFooter.openProfileMenu 与 profileDropdown.profile 静态声明；完整原版 Profile 页面布局尚未确认。

Profile 为应用内页面，复用现有页面、间距、字体、浅色/深色变量。上方头像与昵称，下面紧凑展示 UID、会员与绑定状态，再列收藏夹、观看历史、关注列表和退出登录。后三个业务入口采用禁用样式，不打开虚构数据页面，不增加成段解释。真实头像、昵称不支持编辑；未知会员信息不伪装成非会员。

页面是 B站字段对 Codex 风格的适配，不宣称与原版 Profile 像素级一致。用户指定齿轮下方的位置优先于版本差异。

### 取片与播放

绑定确认后请求一次本软件会话的首页推荐，按服务端顺序过滤明确的广告和直播，取第一个普通视频。记录 BV 号和标题供验收；分 P 视频取第 1 P。若首个普通视频无权播放、失效或当前格式不支持，展示实际原因，不静默换成后续视频冒充第一条。

默认选片后显示标题/封面并等待用户点击播放，不在启动时突然出声；不做首页信息流页面。提供手动刷新选片操作，本次验收固定记录所选 BV 号。

聊天记录中增加 Codex 图片容器风格的视频卡片，拖动右下角调整尺寸。右侧保留 VideoDock 的普通、放大、收起布局。两处共用一个 video 元素与播放会话，显式切换时移动该元素，保留进度、音量和清晰度；非活动位置显示封面与切换入口，不同时播放。播放/暂停、进度条、时间、音量、画质是本轮控件。收起或离开视频所在页面时暂停并保留本次进度；返回不自动出声。不新增跨重启播放进度同步或观看历史上报。

画质列表由当前视频、当前账号返回的权限与实际可播放码流共同决定，不写死 1080P/4K 或仅根据会员徽章推断。第一版优先 H.264 + AAC 的常规 SDR 码流；客户端不支持的 HDR/杜比/HEVC/AV1 等组合不伪装为可播放选项。默认最高可用且不超过 1080P 的画质；用户仍可选接口和当前环境实际支持的更高常规画质。切换保留进度、音量和播放/暂停状态。

## 4. 实现结构

### Electron 主进程

新增 electron/bilibili/ 功能目录，分别负责账号会话、请求/WBI 签名、推荐/视频元数据和播放资源。接口域名、请求参数、签名规则与响应转换集中在这里，React 不依赖 B站原始响应结构。

preload 只暴露专用操作，如获取登录状态、申请二维码、检查扫码、获取 Profile、获取首个推荐视频、准备播放、退出登录。保持 contextIsolation、sandbox 和禁用 nodeIntegration，不通过关闭浏览器安全策略解决媒体访问问题。

本地凭证以 Electron safeStorage 加密后存入现有应用 userData，普通 UI 状态不存 Cookie；加密不可用时如实提示无法持久保存，不降级到明文。B站凭证不传给 React、不写日志或 OpenSpec。持久化只影响本应用目录。

### 播放器

建议依赖 dash.js（处理 DASH 音视频同步和拖动），以现有 video 元素渲染。将 B站 DASH 响应中的时长、编码、初始化段和索引范围转换成 MPD；有明确合适的单文件 MP4 返回时可走原生 video。实施时锁定实际使用的依赖版本，不添加第三方全功能播放器 UI。

由 Electron 提供仅绑定 127.0.0.1 随机端口的媒体中转，给播放器提供 MPD 和当前选中视频的媒体资源，处理 Referer、Range 与响应长度/状态，避免 file 页面直接跨域和拖动失败。请求携带应用本次运行的随机访问标识；只接受主进程登记的资源 ID，不接受任意上游 URL，不将 B站 Cookie 发往媒体 CDN。仅允许本次 B站播放响应中的合适 HTTPS 媒体目标及受限重定向，不扩成通用代理。

中转流式传输，不将整个视频下载到磁盘。换片、退出与关闭应用释放旧资源，停止对应请求。播放 URL 有时效，开始播放或需要重新准备时重新获取，不把临时 URL 持久化为长期播放源。过期/网络失败先报告具体状态并提供手动重试，不循环自动重试。

这一播放器与中转组合是实现建议，尚未运行证明。若实际接口不提供必要 DASH 信息，记录具体阻断点，不以静态分析或无声画面宣布完成。

### React 前端

src/features/account/ 管登录状态、扫码面板、账号菜单和 Profile；src/features/video/ 管视频选择、播放器与控件。ActivityRail 添加头像，App/Titlebar 增加 Profile 路由与标题；数据状态与显示组件分离。

原开发场景、侧栏项目与会话模拟不变。Conversation 中在演示消息组之间插入视频卡片。仅增加实现上述流程需要的状态，不重构全局状态系统。

## 5. 实现顺序与验收

1. 同步已批准的最新阶段限制，建立账号与主进程接口。
2. 接通扫码、手机号状态与持久登录；增加头像和 Profile。
3. 接通首个普通视频选择和视频元数据。
4. 接通有声播放、进度/音量、画质切换及窗口行为。
5. 独立 code reviewer 做静态代码审查，处理实际问题；同步 OpenSpec 进度。
6. 只做两类用户允许的运行验收，登录操作作为视频流程的前置步骤，不建立额外测试套件：
   - 前端布局：现有窗口最小尺寸与常用尺寸、浅/深色、头像菜单/Profile、视频普通/放大/收起，检查遮挡和溢出。
   - 视频功能：用户扫码后绑定状态通过；记录首页第一条普通视频 BV 号；确认实际画面连续推进和声音，播放/暂停、拖动、音量、画质切换保留进度；重启恢复会话后仍可播放，主动退出清除本应用会话。

登录过期与未绑定分支若本次无法自然观察，记为未验证，不伪造账号状态来扩展测试。清晰度少于两档时不得把画质切换标为已通过。只有实际观察到的项目才勾选完成；代码审查不能代替实际画面、声音和视觉验收。

不运行 lint、类型检查、单元测试或全量回归，不因设计完成自动构建/打包。实现阶段的用户扫码与声音确认需要用户参与。生产构建与打包仅在用户要求时执行。

## 6. 实施者可自行决定的事项

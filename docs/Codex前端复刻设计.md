## 已确认的目标

以本机当前安装的 Codex Windows 桌面应用为视觉与交互基准，重新建立 `D:\Codex_Bilibili_Player`。完整保留 Codex 的界面风格和原有文案，覆盖可见页面与本地交互，用复杂开发场景让界面具有连续、可信的使用状态。Bilibili 视频嵌入与视频信息暂不设计，保留空模块。

## 实现路线

选择 Electron + React + TypeScript + Vite。Electron 负责窗口，React 负责页面，本地场景引擎负责演示过程。先从原版包中定位组件、视觉变量和动画，再分别重建可维护模块。

比较过三条路线：

- **采用：依据原版资源模块化重建。** 精确引用已找到的设计参数，同时隔离本地数据与 UI，方便以后接 Bilibili。
- 直接运行完整原版 bundle：会引入账号、服务协议和大量专用后端依赖，不适合独立播放器。
- 在 Cotex_DeskReader 上扩展：借鉴其 Electron 外壳与内容替换思路，但样式要参考rea逆向出的codex桌面端文件，但它的阅读器结构不足以承载完整 Codex 页面。

## 模拟场景

至少四组互有关联的复杂虚构项目，分别提供多个会话、文件、差异和工具记录：

1. **Atlas Console**：React/TypeScript 管理端，权限与路由改造、表格性能问题、接口联调、审查反馈及多文件变更。
2. **Harbor API**：服务端订单流，幂等键、数据库迁移、异步队列和日志定位，包含待批准命令与中断恢复过程。
3. **Orbit Desktop**：桌面端分栏与状态同步，窗口行为、资源加载、主题和键盘交互改造。
4. **Prism Pipeline**：数据处理任务，批处理进度、异常记录、调度运行、报告文档和关联 PR。

数据由本项目编写，使用虚构身份和路径，不复制用户真实聊天、客户资料、凭据或私有代码。工具参数、终端日志、文件差异、执行顺序和最终回复应相互对应，避免随机拼接。

用户发送消息后，按当前项目和明确关键词选择预设场景；未匹配时进入同项目的通用预设流程。流程包含准备、计划、工具运行、等待选择、流式回复、完成/停止等状态。审批会真实改变后续演示分支。刷新恢复已发生记录；正在演示的步骤恢复为可继续状态，不重复生成相同记录。

不在每个页面增加“这是演示”副标题。应用标题、README 和关于页说明这是独立的本地界面演示。不会把模拟后端动作报告为真实的文件修改、测试或发布。

## 模块边界

```text
electron/                 窗口生命周期、系统按钮、窄接口 preload
src/app/                  路由、布局组装、上下文
src/components/ui/        图标、按钮、菜单、弹窗、提示、分栏
src/features/sidebar/     项目、置顶、搜索、归档
src/features/conversation/消息、输入框、计划和工具记录
src/features/review/      文件树、差异、Git 与 PR 演示
src/features/workspace/   编辑器、终端、浏览器、文档标签
src/features/automation/  自动化页面及表单
src/features/skills/      技能列表与详情
src/features/apps/        应用、插件与连接状态
src/features/settings/    分组设置和外观
src/features/work/        内容入口与预览
src/features/video/       留空的后续视频模块
src/scenarios/            分项目数据、脚本步骤、虚构文件
src/state/                类型、状态操作、场景调度、持久化
src/styles/               tokens、基础样式、动画；局部样式归组件
docs/                     研究记录、设计日志、实施日志、来源说明
openspec/changes/replicate-codex-desktop/ proposal、design、specs、tasks
```

布局组件不内嵌长篇场景数据。场景调度不直接操作 DOM。页面只通过状态操作变更数据。以职责拆分，常规组件目标低于 250 行；不为行数拆出无意义抽象。

持久化采用单一应用命名空间，保存会话、场景进度、项目、设置和布局。长文本与文件数据分别组织，避免每个流式字符都全量落盘。原版动画参数集中映射；处理减少动态效果偏好。
